## 1. 产品定位与业务目标

### 1.1 一句话定位

> 云湃工业一体机是**面向制造业的证据治理型全链路 Agent**：一个统筹 Agent 作为唯一业务入口，以 M0 为正式数据基础，把订单、工程、物料、采购、排程、成本、非标设计连成**可追踪、可恢复、可审计**的业务执行链。

产品的最小交付单位是**业务任务**（一个订单从文件到排程的全链），而不是一次聊天回答。这决定了编排层的地位：它是产品的骨架，路由错一步，整条业务链就断一环——这正是本次重构的动机。

### 1.2 解决的五类根问题

| # | 根问题 | v2 编排的对策 |
|---|---|---|
| 1 | 信息重复录入 | 一次上传识别→canonical 落库，全链工具从 canonical 回读装配（装配器单源） |
| 2 | 数据来源丢失 | Goal 信封 evidence 逐字段携带 sheet/行/列/原值坐标，RunState 全程留痕 |
| 3 | 前置事实变化不重算 | 工作流引擎 DAG 依赖：上游步骤产出变化，下游 ready 条件失效即重算（v2 新增） |
| 4 | AI 建议不可交付 | 审查 Agent 合同驱动校验 + 六类人工 Gate；LLM 置信度不得绕过 Gate |
| 5 | 经验不沉淀 | 自进化三族对象（知识/操作模式/产品档案）全闭环迁入并补三缺口 |

六大卖点中的"**受治理的自进化**"是差异化核心：进化产物是**数据不是代码**，晋升要过独立出现阈值与人工决策，运行期受只读红线监测。

### 1.3 目标用户（7 类）

| 用户 | 典型场景 | 主要接触面 |
|---|---|---|
| 工厂/运营负责人 | 订单全链进度、异常与 Gate 审批 | 前端工作台 + Gate 弹窗 |
| 工程（BOM/SOP） | 工程图/BOM 上传识别、SOP 生成 | 上传 + M2 工具链 |
| 采购 | 采购建议导入、PO 审批、供应商回复 | M4 工具链 + 邮件草稿 |
| PMC/计划 | 排程求解、快照、发布、派工 | M5 工具链 + apply Gate |
| 财务/审计 | 成本滚算、对账、审计追溯 | M6 + evidence/ledger 回读 |
| 非标设计 | 非标方案生成（M8） | 子 Agent 层 |
| 管理员/知识治理 | 权限分配、知识候选审批、进化治理 | identity + evolution API |

### 1.4 核心业务流与五条端到端路径

**六段闭环**：理解 → 计划 → 执行 → 校验 → 交付 → 沉淀。对应 v2 三角色：理解+计划（统筹 Agent）、执行（Worker Agent）、校验+交付门（审查 Agent）、沉淀（自进化观察）。

**五条端到端路径**（验收口径）：

1. **订单到计划**：原始文件上传 → M1 解析 → M0 canonical → M2 工程 → M3 需求 → M4 采购 → M5 排程发布（workflow: `m1_m5_document_to_plan`，9 步）；
2. **查询追溯**：任意 canonical 事实反查来源文件与字段证据；
3. **新数据入库**：自描述表识别 → canonical 候选 → 审核 → 发布（识别四件套 + M0 Gate）；
4. **经验自进化**：运行信号 → 知识候选 → 人工固化 → 注入消费（evolution）；
5. **操作自进化**：重复工具序列 → 快捷操作 → 一键复用（shortcuts）。

### 1.5 产品演进路线

- **P0（当前）**：上传识别 → M0 canonical → M1-M5/PMC 真实链路联调；
- **P1**：受治理知识（M1 Governed Wiki 接入、产品档案三源齐备）；
- **P2**：操作自进化（shortcuts 自动触发与 UI）；
- **P3**：模块生态（M7 法务、M8 非标、第三方工具经注册流程接入）。

v2 编排重构是 P0 阶段的**地基工程**：不改变 P0 业务目标，只替换承载它的编排骨架。

以下每条均给出旧代码位置与行为证据；这是"路由都是错的"判断的展开，也是 v2 验收的对照基线。

| # | 痛点 | 旧实现证据 | 后果 |
|---|---|---|---|
| 1 | **LangGraph 图是空壳** | `build_graph()`（graph.py:1002-1016）只服务 Studio；生产 `api.py:47` 用 `YunpaiGraph.run()` 手写循环（graph.py:369-377） | 改图不影响真实执行；checkpointer/interrupt/并行能力全部缺席 |

### 3.12 重构边界结论

**推倒重建的**：执行引擎（手写循环→真 StateGraph）、路由（三套叠加→单一决策链）、装配（双份→单源）、审查（硬编码→合同驱动）、配置（三处→单一来源）。

**原样保留的**：工具合同（115 manifest + Goal 信封）、本地工具 handler 业务实现、8 个 SQLite 库及其建表代码、识别四件套、Gate/resume/CAS 授权机制的业务语义、evolution 包、全部可搬测试。

## 4. 重构目标与设计原则

### 4.1 总目标

> 编排层从零重建：LangGraph StateGraph 为唯一执行路径；统筹/Worker/审查三角色分工；工具与技能先迁移后逐个审查注册；自进化闭环补全；对外 API 契约兼容。验收线：W913 订单 workflow 路径 m5.released，且 free 路径全链跑通（修复 §3.4 死点）。

### 4.2 七条设计原则

1. **唯一执行路径**：业务只走编译后的 StateGraph（checkpointer 持久化、interrupt 人工门）。不存在第二套循环；Studio 与生产用同一个图。
2. **装配单源**：全系统只有一个装配器（PayloadAssembler），free 与 workflow 共用同一份桥接规则表；消灭 `_payload_for` 与 bridge 的双实现。
3. **合同驱动审查**：审查规则挂在工具合同（review_gate 元数据 + 规则表），不在代码里 if 工具名；新增工具=新增数据，不改审查代码。
4. **语义自由，非事实自由**（沿用 09-06 铁律）：Agent 只做意图路由/文件分类/字段映射提案；事实值、计算引擎、护栏永远确定性；输出必过 schema 校验；事实字段必带证据坐标。
5. **路由目录只含已绑定工具**：LLM 路由提案的候选集 = `BOUND_LOCAL ∪ BOUND_HTTP` 工具 + 已注册技能 + 已知 workflow，从根上杜绝"提案不存在的工具"。
6. **进化闭环真实消费**：进化产物必须被统筹 Agent 在路由/分发时真实消费，且使用结果回流 record_usage；只改运行库不改代码（只读红线）。
7. **API 契约兼容**：/runs、/runs/stream（NDJSON 事件）、resume、上传的请求/响应结构不变；以旧实现为契约快照基线做回归测试。

### 4.3 非目标

- 不重写工具业务语义（M0-M5 handler 只迁移不重写；M3/M4 假 fixture 明确标注 sandbox 级）。
- 不改前端、不改数据库 schema、不引入向量库、不做 M6-M8 新功能。
- 不在本阶段处理 M0 的 20 个未实现端点与 M2 外部服务依赖（属旧仓库在途工作）。


### 5.3 一次 run 的完整生命周期（文字时序）

1. **进入**：POST /runs（message、attachments、可选显式 workflow/tools/skills、tenant/principal 头）→ API 层创建 thread_id+run_id，注入 graph.ainvoke。
2. **统筹-理解**：路由决策器按 §6.2 决策链输出 RouteDecision（source/confidence/reason 留痕），写 messages。
3. **统筹-计划**：workflow 路径按 JSON 展开为 DAG 步骤集；free 路径把 tools/skills 列为步骤；计划写入 state.plan。
4. **循环执行**：每轮分发→装配→执行→审查；装配缺口返回 BLOCKED_INPUT 时，统筹决定补数（data Gate）或重排。
5. **人工门**：审查判定需人工 → `interrupt()` 挂起（state 由 checkpointer 持久化）；前端看到 gate_pending 事件；POST /runs/{id}/resume 携带决策 → `Command(resume=...)` 恢复；Gate 决策写入 approvals 并回流进化库。
6. **终态**：全部步骤完成 → finalize 生成 summary；进化观察节点提取五类信号（异常吞掉，不破坏 run）。
7. **流式**：全程 astream 映射为旧 NDJSON 七事件契约（快照测试锁定）。

## 6. 统筹 Agent 设计思想

### 6.1 职责

**理解、路由、计划、分发、知识消费**——统筹 Agent 是"按工作流工作"的调度大脑：

1. 意图理解与路由决策（workflow/free/chat 三值）；
2. 计划生成：workflow 展开（拓扑序步骤集）、free 步骤列表（tools+skills）、chat 直接应答；
3. 步骤分发：每轮挑"依赖已满足"的步骤交给 Worker（v2 保留单步执行起步，调度器天然支持多就绪步骤，为并行留口）；
4. 异常处置：BLOCKED_INPUT → 决定补数（data Gate）/跳过/终态；重试有上限；
5. 会话记忆维护（messages）与进化知识消费。

**统筹 Agent 绝不做**：调用工具（那是 Worker）、放行或否决业务结果（那是审查 Agent 的确定性规则与人工 Gate）、编造任何事实值。

### 6.2 路由决策链（单一机制）

```
1. 显式参数（一票否决）：request.workflow / request.tools / request.skills
   → route=workflow/free（source=explicit）
2. LLM 提案（默认路径）：
   输入 = message + 附件元数据(嗅探格式) + 【已绑定】工具目录(名称+一句话描述)
          + 技能目录(满足偏序) + workflow 目录 + 活跃进化知识(注入)
   输出 = {intent, route, workflow_id?, tools[], skills[], confidence, reason}
   校验 = route 枚举 ∧ workflow_id∈KNOWN ∧ tools⊆BOUND ∧ skills⊆SKILLS∧偏序
   通过 → source=llm；任何失败/非法 → 落 3
3. 最小确定性回退（source=deterministic_fallback）：
   - 有原始业务附件 → workflow=m1_m5_document_to_plan
   - 有 canonical 标识 → workflow=canonical_to_m5
   - 否则 → chat（附"可用能力建议"）
```

与旧实现的本质区别：**第 3 步只剩最小规则**（旧版 240-303 行的关键词大表全部删除）；**LLM 的输入目录经过绑定状态过滤**（旧版喂全量合同）。`route_decision` 三元组（source/confidence/reason）保持留痕兼容。

### 6.3 工作流引擎

- workflow 定义沿用 JSON（`workflows/m1_m5_document_to_plan.json`、`canonical_to_m5.json`，含 invariants），加载时校验：无前向依赖引用、无环、步骤工具必须 BOUND。
- **DAG 真实调度**：步骤 ready = depends_on ⊆ completed；替代旧的"数组序+next_step_index"。
- 步骤状态机：pending → ready → running → completed/failed/blocked/skipped；上游重做时下游标记 stale（供"前置事实变化不重算"问题的后续演进）。

### 6.4 会话记忆与知识消费

- `messages` 用 LangGraph `add_messages` reducer 真实累积（user/assistant/tool 消息）；`thread_id` 关联同一会话的多次 run，Planner 决策时携带近窗口历史。
- 进化注入的活跃知识进入两个消费点：路由 prompt（"历史上同类任务常用工具序列"）与分发上下文（快捷操作建议）。消费与否写 `knowledge_consumed`，供进化侧统计命中率。

## 7. Worker Agent 设计思想

### 7.1 职责

**装配、调用、信封**——Worker 是唯一的工具执行者：

1. 接收统筹分发的步骤（tool 或 skill）；
2. 用**唯一装配器**构造 payload；
3. `ToolRegistry.call(name, payload, ctx)`：输入 schema 校验 → handler（本地或 HTTP）→ 输出 schema 校验 → Goal 信封（status/code/missing_fields/conflicts/evidence/source/gate/idempotency）；
4. 步骤记录（StepRecord：tool/payload 摘要/结果摘要/耗时/trace_id）。

### 7.2 唯一装配器（本重构最关键的收编）

旧系统装配有两份：workflow 路径的 `bridge_payload`（orchestration_bridge.py:902+，W913 验证可跑全链）与 free 路径的 `_payload_for`（graph.py:765-999，11 个工具分支+空 dict 兜底）。v2 合并为**一个装配器 + 一份声明式桥接规则表**：

```
assemble(tool, ctx):
  1) 合同默认值（manifest input_schema defaults）
  2) 显式参数（request[tool]）
  3) 桥接规则（BRIDGE_RULES[tool]：从前序步骤产出字段/canonical 回读/附件上下文取值）
  4) jsonschema 校验
  5) 缺口 → BLOCKED_INPUT{missing:[{field, expected_from, hint}]}（结构化，不再静默空 dict）
```

规则表覆盖旧 bridge 的全部映射（M1→M0、M0→M2、M2→M3、M3→M4、M4→M5、M5 快照/求解/回读），并补齐 free 死点工具 `ingest_m5_planning_snapshot`、`get_m5_schedule`、`data_import_status` 的规则。**规则表是数据**（rules.py 中集中声明 + 测试锁定），新增工具=新增规则行。

### 7.3 技能分发

Skill 保持两层概念（面向统筹的高阶能力，内部编排多个 tool）。沿用 `_dispatch_registered_tool` 模式（skills.py:226-261）：技能 operation 经操作映射表落到具体 tool，**必须经 ToolRegistry.call，不可绕过工具契约**。8 个默认技能与 M1/M3/M4 操作映射表迁移；`SKILL_USAGE_ORDER` 偏序校验保留。

## 8. 审查 Agent 设计思想

### 8.1 职责

**执行前授权、执行后审查、Gate 生命周期、反馈进化**：

1. **preflight**：按合同声明的副作用/角色要求做执行前检查（写操作需授权步骤、生产 transport 护栏）；
2. **post 审查**：按规则表对结果做确定性检查（置信度阈值、生命周期状态、回读核验、fail-closed 字段）；
3. **Gate**：六类人工门（M0 candidate / M1 review / M2 engineering / M4 procurement / M5 apply / data supplement）——触发即 `interrupt()`，审批后 `Command(resume=...)` 恢复；角色矩阵 `GATE_ALLOWED_ROLES`（graph.py:456-465）迁移为数据表；
4. **使用反馈**：每次 Gate 决策与 run 终态调用 `evolution.record_usage`（补缺口①）。

### 8.2 合同驱动规则表

审查规则从代码迁到数据：每个工具的规则 = manifest `review_gate` 元数据 + 规则注册表条目（when 条件 → pass/gate:<name>/fail 动作）。旧 if-elif（agents.py:388-449）逐条迁移为规则条目，**迁移对照表在书二 §6.1**（审计要求：旧分支全集 ≡ 新规则全集）。

### 8.3 Gate 生命周期与 resume 语义（业务语义不变）

沿用已验收的六类 Gate 决策语义：review/candidate/engineering/apply → approve；data → retry+supplement；procurement → retry+supplier_by_material。风险教训写入规则注释：**engineering Gate 不得误当 retry 使用**（否则 M2 步骤反复 supersede 卡死——旧 AGENTS.md 明确警告）。LLM 置信度≥阈值**不得**自动 approve（旧审计 P0：绕过人工 Gate 违反自由化原则）。

## 9. 数据与知识架构

### 9.1 8 库沿用（§2.4 表）

v2 打开同一套库文件（env 可指到新 runtime 目录；evolution/canonical/recognized/business-catalog/m5 五库**连数据一起迁移**，runs/identity/sandbox 可新起）。runs 库新增 `langgraph_checkpoints` 表（官方 SqliteSaver 格式，只增不改），业务查询仍走 runs 表（双写：checkpointer 存执行状态，runs 表存业务视图摘要）。

### 9.2 M0 canonical 目标态

PG 四 schema 16 表（core/knowledge/staging/audit）+ 全表 tenant_id + RLS 是目标态；现实约束（沿用治理红线）：本机无 PG、RLS 未实测、双租户用例挂 GB10 环境。v2 不改变该目标，也不阻塞在它上面——本地沙箱继续承载联调，`YUNPAI_TOOL_TRANSPORT=http` 时 M0 走真实服务。

### 9.3 知识四块的接法

摄取流水线与识别四件套**原样迁移**（它们与路由无关，正是旧系统里最健康的部分）；M5 案例库随 m5_repository 迁移；M1 Governed Wiki 合同迁移后绑定 HTTP（服务在 GB10）；产品档案随 evolution 包迁移。**不引入向量库**。

### 9.4 数据红线（沿用）

- 候选 ≠ canonical 主数据；文件上传成功 ≠ 事实可用；模型推断必须标 `inferred=true`。
- PMC 九项硬数据缺口未补齐前，真实排程只能到候选/草稿/blocked，禁止生产放行。
- 敏感信息（身份证/银行卡/工资）脱敏传送与存储；原始敏感文件不进 git。
- HTTP 200 ≠ 落库成功（fail-closed 回读核验）；202 ≠ 完成（有界轮询）。

## 10. 自进化机制设计

### 10.1 三族进化对象（沿用）

3. **产品档案** pu_product_profiles + pu_field_evidence（BOM/SOP/工程图三源，字段级证据三态）。

### 10.2 全闭环设计

```
运行信号(五类提取器,只读 RunState)
  → 候选(结构指纹, UNIQUE(tenant,kind,fingerprint))
  → 晋升检查(独立出现≥3 次防同任务刷分 / 强证据 1 次 / 「稍后」冷却 7 天 / 敏感内容拦截 / entity_type 白名单)
  → 人工决策(approve / approve_modified / reject / later; 产物是数据不是代码)
  → 注入(确定性结构化匹配 top-5)
  → 【v2 补】消费(统筹路由 prompt + 分发上下文)
  → 【v2 补】使用反馈(record_usage: confirmed/contradicted; 反例≥2 自动 suspend)
  → (闭环回到候选库的 usage 统计)
```

## 12. 审查注册制度（先迁移，再逐个审查注册）

### 12.1 五项 checklist（每个工具/技能注册前逐项过审）

1. **合同**：manifest input/output JSON Schema 加载校验通过；failure_codes 完整；
2. **绑定**：绑定状态明确（BOUND_LOCAL：有 handler 且测试过 / BOUND_HTTP：有服务地址与适配器 / SANDBOX：本地假实现明示 / UNBOUND：不得进路由目录）；
3. **装配**：装配器有该工具的规则行或确认"仅显式参数"；缺口行为=BLOCKED_INPUT；
4. **审查**：review_gate 规则条目存在（含 preflight 角色要求与 post 检查）；需要人工 Gate 的工具列明 Gate 类型；
5. **测试**：契约测试（schema 双校验）+ 装配测试 + （BOUND_LOCAL）回读断言各至少一条。
