## 0. 怎么用这本手册

- 每个功能一张**功能卡**，固定回答六件事：**是什么 / 为了什么 / 给谁用怎么触发 / 编排怎么走 / 用到什么 / 验收要点**，最后一行是**需求出处**（指向旧仓库 `.project-to-act/docs/` 的具体文档与章节）。
- **审核方式**：你逐卡核对"这是不是我要的功能"，驳回标卡号（如 F-C07）；卡面与你的需求不符就是这本手册的错，改卡不改需求。
- 三书分工：**书三管"做什么、为什么"，书二管"怎么做（代码级），书一管"为什么推倒重来**。卡里"编排怎么走"只写业务流程，技术细节一律引书二章节。
- 需求文档索引见附录 C；本手册的需求原话均来自这些文档，没有一条是凭空写的。

> **背景答疑：为什么旧系统会有两套执行路径？** 不是设计出来的，是长出来的：手写执行循环先出现（为了精确控制流式事件、Gate 挂起、逐步装配），后来为了接 LangGraph Studio 调试又补了一个编译图，生产从未切换过去，两边靠人肉同步。v2 只留一套：Studio 和生产用同一个编译图（书一痛点 1 / 原则 1）。

## 1. 产品总纲（需求原点）

### 1.1 一句话定位

> "把一个工厂『从接订单到排出可执行生产计划』的全部过程，装进一个有证据治理的 AI Agent 工作台。"（10-需求文档-重构稿）

### 1.2 五类根问题（产品存在的理由，01§1）

| # | 根问题 | 一句话对策 |
|---|---|---|
| 1 | 信息重复录入 | 一次上传识别 → canonical 全链复用 |
| 2 | 数据来源丢失 | 每个字段带文件/行/列证据 |
| 3 | 前置事实变化不重算 | 工作流 DAG 依赖（v2） |
| 4 | AI 建议不可交付 | 确定性校验 + 人工 Gate |
| 5 | 经验不沉淀 | 自进化三族对象闭环 |

### 1.3 五条设计原则（01§1 原话）

① 一个根入口；② M0 管正式事实、模块管运行事实；③ 模型理解规划 + 代码约束执行；④ 默认自动继续、异常统一 Gate；⑤ 候选 3 个独立任务或强证据才晋升。

### 1.4 产品魂

> RQ-8："AI 不确定/缺数据时系统停下问我，绝不编。"（10-重构稿）

### 1.5 六段闭环与五条路径

理解→计划→执行→校验→交付→沉淀（六段）；订单到计划 / 查询追溯 / 新数据入库 / 经验自进化 / 操作自进化（五条端到端路径，验收口径）。

### 1.6 演进方向

"从把链路跑通转向**让中小企业用得起来**"（10-重构稿）；本地一体机部署、数据不出厂；7 类用户（厂长/工程/采购/PMC/财务/非标/管理员）。

## 2. 编排平台功能（统筹 Agent 自身提供的能力）

### F-P01 意图路由与统一对话入口
- **是什么**：用户（7 类角色）用一句话+附件发起任何业务请求，统筹 Agent 识别意图，决定走受控工作流、自由工具组合还是对话解答。
- **为了什么**：根问题 1/4——一个入口贯穿业务链，不再让用户在十几个功能页里找入口。
- **给谁用/怎么触发**：前端对话框 / POST /api/runs；可带附件（订单/BOM/SOP/工程图）。
- **编排怎么走**：显式指定 > LLM 提案（只喂已绑定工具目录）> 最小确定性回退（书二 §4.1）；决策留痕 route_decision。
- **用到**：Router、已绑定工具目录、活跃知识注入。
- **验收要点**：route 只有 workflow/free/chat 三值；LLM 不可用时回退不中断；决策来源可审计。
- **需求出处**：01§3"一个根入口、一个根执行者"；04§3。

### F-P02 受控工作流（两条主链）
- **是什么**：把多模块长链固化成版本化工作流：`m1_m5_document_to_plan`（原始文件→排程，9 步）与 `canonical_to_m5`（订单已入库→排程，7 步）。
- **为了什么**：长链业务不该靠用户逐步点，也不该靠 LLM 即兴串——固定顺序+依赖，可断点可审计。
- **给谁用/怎么触发**：上传原始文件自动触发前者；订单已在 canonical 后触发后者。**前端上传必须发 `workflow:"m1_m5_document_to_plan"`（发错会导致 M1 415——04§4 已写死为契约）**。
- **编排怎么走**：v2 升级为 DAG 依赖真实调度（书二 §4.3）；旧 m0_m5 已删除不恢复。
- **验收要点**：步骤依赖参与调度（书二 test_workflow_dag）；两条链均可在 W913 真实数据跑通。
- **需求出处**：01§4 编排层；04§3。

### F-P03 人工 Gate（六类统一闸门）
- **是什么**：异常/关键动作统一停下等人：M0 candidate（候选发布）、M1 review（低置信文档）、M2 engineering（工程确认）、M4 procurement（采购/供应商事实）、M5 apply（排程发布）、data（补数据）。
- **为了什么**：根问题 4——AI 建议必须经人放行才可交付；"默认自动继续，异常统一 Gate"。
- **给谁用/怎么触发**：审查 Agent 按合同规则自动触发；前端弹窗显示决策项（允许/拒绝/暂停修改）。
- **编排怎么走**：v2 用 LangGraph interrupt 挂起 + resume 恢复（书二 §3.4/§6.2），语义与旧系统一致。
- **验收要点**：**LLM 置信度任何值都不得自动 approve**（旧审计 P0 教训）；Gate 决策留 approvals 痕迹并回流进化库。
- **需求出处**：01§3 原则④；04§3。

### F-P04 断点续跑（run 持久化与 resume）
- **是什么**：任何 run 中断（Gate 挂起/异常/主动暂停）后，可从断点恢复继续；决策动词 approve|allow|continue|retry|reject|stop。
- **为了什么**：长链任务不能因一次中断全部重来；可恢复是交付承诺（可追踪、可恢复、可审计）。
- **编排怎么走**：checkpointer 持久化 + runs 表业务视图（书二 §3.3）；resume 走 Command 恢复。
- **验收要点**：Gate 挂起→resume→状态与审批留痕完整；受信主体缺失时 resume 403（安全红线）。
- **需求出处**：04§3（YUNPAI_REQUIRE_TRUSTED_PRINCIPAL）。

### F-P05 流式进度与全链 trace 审计
- **是什么**：run 全程 NDJSON 流式事件（run_start/assistant_delta/step_start/step_result/gate_opened/run_error/run_done）；全链 trace 可查（get_business_order_trace 等 ORCH-001~020）。
- **为了什么**：厂长/财务要"看得见过程"；审计要"查得到每一笔"。
- **编排怎么走**：图事件→旧七事件契约转换（书二 §8.3），前端零改动。
- **验收要点**：事件与旧实现逐字段一致（契约快照测试）；快照 content_b64 脱敏为 [omitted]。
- **需求出处**：04§3§4。

## 3. 数据入库与主数据（M0 + 识别链）

### F-D01 原始文件上传与格式识别
- **是什么**：上传任意业务文件（XLSX/XLS/PDF/DOCX/图片/压缩包，≤40MiB/文件、2000/批），系统双因子嗅探格式（magic bytes+扩展名）并采样（表头+前 N 行 / PDF 渲染图）。
- **为了什么**：入库的第一道门：先知道"这是什么文件"才谈识别；防伪扩展名文件混入。
- **给谁用/怎么触发**：工程/采购/PMC 上传；POST /api/uploads。
- **编排怎么走**：附件预处理→sniff+采样元数据进 attachments[]（书二 §10）。
- **用到**：file_sniff、media_sample、sample_file 工具。
- **验收要点**：坏文件/伪扩展名被拒且不中断批次；采样含 PII 脱敏。
- **需求出处**：01§4 M0/M1；04§4 上传契约。

### F-D02 订单识别与字段映射（AI 理解、绝不编造）
- **是什么**：对订单表做 AI 列映射（哪个列是产品编码/数量/交期…），代码按映射全量抽取行；每次解析产出 m1.document.v2 证据产物（SHA-256/MIME/源坐标/置信度/证据引用）。
- **为了什么**：根问题 1/2——把"散落的 Excel"变成带证据的结构化事实；**"AI 干理解、不干编造"**。
- **给谁用/怎么触发**：上传订单文件后自动进入 m1_parse 步骤。
- **编排怎么走**：map_to_canonical（多模态 LLM）→ canonical_schema 校验 → 全量抽取（书二 §10）；**缺字段留空+issue，不填 0/默认值**（04§2-M1 原话）。
- **用到**：tabular_extract、order_semantics/order_parser_v2/order_workbook、ingest_document。
- **验收要点**：字段级证据坐标齐全；低置信（needs_review 或 overall_confidence<0.8）自动开 M1 review Gate。
- **需求出处**：01§4 M1；04§2-M1。

### F-D03 自描述表落库与查询
- **是什么**：任意"自描述表"（有表头的数据表）免建模落库：采样→识别→存为带列描述的表，可按列过滤/聚合查询。
- **为了什么**：工厂大量临时表格进不来 canonical 体系，先可查可用，再逐步晋升。
- **给谁用/怎么触发**：管理员/工程批量整理资料；free 路径调 sample_file→ingest_recognized→query_recognized_table。
- **验收要点**：sha256 幂等（同文件不重复入库）；PII 脱敏。
- **需求出处**：01§4 识别四件套；账本 F-008。

### F-D04 canonical 导入七层管道与正式发布
- **是什么**：候选数据经 upload→status→preview→resolve→commit（→rollback/history/quarantine）七层管道受控入库；九类主资料 facade（产品/订单/BOM/物料/供应商/设备/路线/工序/模治具）单事务发布进 canonical。
- **为了什么**："全厂只认一份事实"——M0 是正式数据基础，发布可回滚可审计。
- **给谁用/怎么触发**：数据管理员/工程；受控工作流 m0_ingest/m0_publish 步骤，或 free 路径显式调用。
- **编排怎么走**：commit 前必须 resolve；发布走 M0 candidate Gate（书二 §7.3 M0 表）。
- **验收要点**：**HTTP 200 ≠ 落库成功——发布后回读 approved_candidates/ledger_count 非零才认成功（fail-closed）**（04§2-M0 原话）；单事务+Outbox。
- **需求出处**：01§4 M0；04§2-M0。

### F-D05 候选晋升门禁（防脏数据）
- **是什么**：识别/导入产物一律先为候选；**至少 3 个独立任务出现或命中强证据（M0 正式版本/正式 Schema/人工纠正成功结果）才晋升为正式事实**；同 Trace 重试、同哈希副本、同一业务记录重复拉取不计独立证据。
- **为了什么**：防偶发错误和刷分污染 canonical——"候选 ≠ canonical 主数据"。
- **编排怎么走**：晋升检查在审查 Agent + 进化库 gate（书二 §6/§11）。
- **验收要点**：防同任务刷分（COUNT DISTINCT task_id）；强证据 1 次即可提议（human_correction 风险最低）。
- **需求出处**：01§3 原则⑤；自进化设计稿"门禁"节。

### F-D06 业务资料目录批量扫描
- **是什么**：把整个资料目录（如微信下载目录）批量扫描入库：递归解包（zip/rar/7z）→逐文件分类→候选库（带文件类型/敏感度分级）。
- **为了什么**：工厂资料散落各处，先全量收进来分类，才谈治理（账本 F-007 已验收过一次 441 文件审计）。
- **给谁用/怎么触发**：管理员一次性导入历史资料；business-data-identification 技能。
- **验收要点**：压缩包安全递归（防 zip bomb）；敏感度汇总报告。
- **需求出处**：skills/business-data-identification；账本 F-007。

### F-D07 canonical 查询与产品图谱
- **是什么**：产品 360° 总览（get_m0_product_overview/graph 1-3 跳关联）、文档清单、库存/实体查询。
- **为了什么**：查询追溯路径的底座——任何事实可反查来源。
- **验收要点**：跨租户查询 404 不泄露存在性；租户缺失 fail-closed。
- **需求出处**：01§4 M0；04§2-M1（同款租户规则）。

## 4. 订单到计划主链（M1→M5，产品主干）

### F-C00 主链总览（用户视角的一天）

用户上传订单 Excel → 系统识别字段（M1）→ 数据入库成候选（M0）→ 人工确认后发布 canonical → 系统生成 BOM/SOP 工程草案（M2）→ 工程师确认 → 系统算缺料（M3）→ 生成采购建议→PO 审批（M4）→ 齐套后排程求解（M5）→ 人工批准发布 → 派工到部门（每步可暂停/恢复/审计）。对应六段闭环"订单→工程确认→缺料→采购→排程→派工反馈"（10-重构稿）。

### F-C01 M1 文档解析（订单变结构化事实）
见 F-D02（同一条链的起点）。补充：解析可能 202+轮询（M1_POLL_BUDGET_S=90 有界轮询，**202 绝不当完成**）；检索过滤支持 interface/length/color/connector 等业务字段；export_m1_order 可导出 XLSX 四 Sheet 复用识别结果。出处 04§2-M1。

### F-C02 M0 落库与发布
见 F-D04。主链第 2-3 步（m0_ingest→m0_publish）。

### F-C03 M2 BOM/SOP 工程生成（订单变工程事实）
- **是什么**：基于 canonical BOM/工艺生成 BOM 控制版与 SOP（80806-129 格式 Word），输出 bom_generation/sop_generation/open_customer_questions 三段。
- **为了什么**：订单只有变成工程事实才能算料算工——"订单转工程事实"。
- **给谁用/怎么触发**：工程确认环节；主链 m2_engineering 步骤；产出走 **M2 engineering Gate**（工程师批准/驳回/答疑）。
- **编排怎么走**：M2 服务不可用（HTTP_UNAVAILABLE/TIMEOUT）时编排器转为可恢复的 data Gate（BLOCKED_INPUT），不硬失败（04§2-M2）。
- **验收要点**：SOP 格式合规；**engineering Gate 不得当 retry 用**（会反复 supersede 卡死——旧 AGENTS.md 警告）。
- **需求出处**：01§4 M2；04§2-M2。

### F-C04 M3 物料需求计算（缺料测算）
- **是什么**：按 BOM 展开算物料需求：**gross=订单量×单耗×(1+损耗)；shortage=max(0, gross−available)**；库存/在途由 Provider 自查。
- **为了什么**：回答"这单缺什么料、缺多少"——采购的前置。
- **给谁用/怎么触发**：主链 m3_mrp 步骤（M2 工程确认后自动）。
- **验收要点**：公式结果可复算（确定性引擎，非 AI）；inventory[*].received_at 必填（04§2-M3）；M5 反向物料需求（receive_m3_material_demand）幂等受理防重复扣减。
- **需求出处**：01§4 M3；04§2-M3。

### F-C05 M4 采购建议→PO→审批
- **是什么**：M3 的缺料转采购建议→生成 PO→采购员审阅（submit-review/approve/request-changes）→确认发单。
- **为了什么**：AI 建议可交付——建议不只是报表，而是可审批可执行的 PO。
- **给谁用/怎么触发**：采购员；主链 m4_procurement 步骤 + M4 procurement Gate。
- **验收要点**：**全程 CAS**（expected_revision+expected_checksum，防并发覆盖）；tenant+site+idempotency_key 必填。
- **需求出处**：01§4 M4；04§2-M4。

### F-C06 供应商协同与供应可视化
- **是什么**：询价/订单邮件草稿生成→供应商回复解析→人工确认供应商事实；到料追踪、预警扫描、催单消息、物料供应快照。
- **为了什么**：把"微信里问供应商"变成留痕闭环；供应状态可视化。
- **验收要点**：**无权威数据时 received/open/ETA 返回 null 而非估算——不编造**（04§2-M4）；供应商事实确认走 procurement Gate（supplier_by_material 语义）。
- **需求出处**：01§4 M4；04§2-M4。

### F-C07 M5 排程求解（计划的核心）
- **是什么**：齐套后求解排程：输入六类计划快照（含 source_observed_at 逐来源新鲜度校验，24h），输出可执行生产计划（批次/工位/时间窗）。
- **为了什么**：产品终点——"排出可执行生产计划"；固定算法引擎（非 AI），跨窗口排程已修复验证（W-H128 feasible）。
- **给谁用/怎么触发**：PMC；主链 m5_snapshot→m5_solve 步骤。
- **编排怎么走**：solve 幂等（幂等键+expected_head_plan_version CAS）；**pressure_only 不得发布**；**缺事实 BLOCKED_INPUT 不补默认值**（宁可停下问人——RQ-8 的排程版）。
- **验收要点**：六类快照完整；同输入重放幂等；新鲜度不过关即阻断。
- **需求出处**：01§4 M5；04§2-M5。

### F-C08 排程发布与派工
- **是什么**：draft 计划经 **M5 apply Gate** 人工批准→released；派工到部门（部门消息走耐久 Outbox）；仅 released 可派，无 MES 对接时只回 pending 不虚发。
- **为了什么**："派工反馈"段闭环；发布是不可逆关键动作必须人批。

### F-C09 canonical 直排工作流
- **是什么**：订单数据已在 canonical（此前发布过）时，跳过 M1/M0 直接 canonical_verify→M2→…→M5 的 7 步链。
- **为了什么**：不重复识别；两条入口覆盖"新文件"与"老订单改排"两种日常。

### F-C10 排程案例库

- **验收要点**：record 只接受已持久化 plan_version（fail-closed）。

## 6. 自进化（受治理的"越用越好用"）

需求原点（用户 2026-09-08 口述）："**越用越好用；经验沉淀弹窗固化；产品全链路理解；暂不允许修改编排与 AGENT.md**；优先 27B 本地模型，允许满血 DeepSeek 兜底。"

### F-E01 经验沉淀（四类信号→弹窗固化）
- **是什么**：系统观察四类信号——**重复操作**（稳定处理顺序）、**经常出错**（错误复发条件）、**经常做对**（成功映射）、**人工纠正**（纠正后的正确映射）；攒够门禁弹窗请用户固化（批准/修改后批准/拒绝/稍后）。
- **为了什么**：根问题 5"经验不沉淀"；把"老师傅的纠错"变成系统资产。
- **为什么是 3 次才弹**：普通候选至少 **3 个独立任务**或强证据才晋升（防偶发误固化+防刷分：同 Trace 重试/同哈希副本/同一记录重复拉取不计）；human_correction 属强证据 1 次即弹（风险最低）。
- **交互细节**：弹窗必展示五要素（触发条件/步骤/参数模板/证据/影响范围+回退方式）；observed 阶段完全静默；每用户每天同类最多 3 张；"稍后"冷却 7 天。
- **验收要点**：**产物是数据不是代码**（active 知识+快捷操作），执行仍走三 Agent+Gate；原始设计的 workflow 提案因此降级为 patterns/shortcuts（设计稿唯一实质裁剪）。
- **需求出处**：自进化设计稿 EV 章；账本 F-028。

### F-E02 知识注入与消费
- **是什么**：固化的 active 知识在后续任务中自动注入统筹 Agent（"这类文件上次怎么映射的/这类错误上次怎么解的"），v2 补上**真实消费**（进路由上下文）与命中率统计。
- **为了什么**：固化了不用等于没沉淀；可度量收益——同类人工操作次数下降、同 fingerprint BLOCKED 复发率下降、识别需人工补字段数下降。
- **验收要点**：注入只作建议不作约束；反例 contradicted≥2 自动停用（v2 接通 record_usage 闭环）。
- **需求出处**：设计稿；书二 §11.2 缺口②修复。

### F-E03 快捷操作（操作自进化）
- **是什么**：重复工具序列固化为可固定（pin）的快捷操作（步骤+参数模板），一键复用。
- **为了什么**："操作自进化"路径；高频流程从 N 步对话变 1 键。
- **需求出处**：设计稿 ok_shortcuts；五条端到端路径之五。

### F-E04 产品理解（产品全链路档案）
- **是什么**：以 product_code 为主键建产品档案，**从 BOM 学物料构成、从 SOP 学工艺工序、从工程图学几何物理特征**——处理 W-H909 时系统知道"这是 1.5m HDMI 2.1 光纤线、铝合金外壳、编织网外被、需要哪些工序"。
- **"理解了"的可计算定义**：任意 product_code 毫秒级返回**字段级带证据、带置信度、可一键溯源**的全链事实卡片；新文档进入自动增量更新（同值多独立来源→置信度升高；冲突暴露进人工 Gate；纠正自动写别名候选——"下次同名文件自动归位"）。
- **同类型推理**：未见过的新型号按规格签名+家族前缀推导（低置信 0.1 草稿须人工确认）。
- **验收要点**：5000 字段/100 产品压测精确（已验）；DWG 工程图为二期（EV-3）。
- **需求出处**：设计稿 PU 章。

### F-E05 只读红线与进化治理
- **是什么**：进化对 workflows/skills/AGENTS.md/src/migrations/registry 一律**只读**，运行期文件哈希监测（v2 加周期检查）；治理台管理候选/证据/晋升/暂停/回滚。
- **为了什么**：用户约束"暂不允许修改编排与 AGENT.md"；进化产物是数据，改代码的事永远归人。
- **验收要点**：测试直接断言"跑完一轮沉淀后编排与 AGENTS.md 哈希不变"。
- **需求出处**：设计稿红线节；书二 §11.3。
